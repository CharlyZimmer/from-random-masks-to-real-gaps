# exp02_finetuning — Sample-Count Ablation (Sentinel)

Sentinel port of `esdc/experiments/exp02_finetuning/sample_ablation/`.
Results are in `results/RESULTS.md`.

## What this ablation tests

`exp02_finetuning` fine-tunes the `exp01_zero_shot` checkpoint on the
available gap-filling training set (joining `$S2_LMDB_PATH` with
`$S2_GAP_FILLING_TRAINING_DIR/lmdb/gap_masks.lmdb` by idx manifest, see
`model_gap_aware/lmdb_training.py::PretrainGapMaskJoinDataset`). This
ablation varies the number of fine-tuning samples, using the same sample
counts as ESDC's own ablation:
**50, 100, 200, 400, 800, 1600, 3200, 6400, 12800** (a doubling series),
each fine-tuned for **20 epochs** (isolating sample count, not training
length) and evaluated on the same canonical eval set as every other Sentinel
experiment (`$S2_DATA_DIR/gap_filling`).

This ablation does not change `exp02_finetuning` itself.

## Method — what's identical / different vs. exp02_finetuning

Identical across all 9 variants: pretrained source (`exp01_zero_shot`'s best
checkpoint, auto-discovered), model architecture (`embed_dim=192, depth=12,
num_heads=3, decoder_heads=1, patch_size=4`), effective peak fine-tuning LR
(4e-5), training/eval LMDBs and eval dataset, `gap_only_masking=True`.

Different: `max_samples` capped per variant, `warmup_steps`
recomputed per variant (see below), separate `training.log_dir` per variant
so all 9 checkpoints coexist under `sentinel/lightning_logs/`.

**n0050/n0100/n0200 additionally differ in `devices`/`base_lr`** vs.
n0400-n12800 — same split ESDC's ablation uses, and for the same reason: at
small N, 4-way DDP with `batch_size=8` (Sentinel's default, vs. ESDC's 16)
leaves too few samples per replica per epoch. These 3 configs use
`devices: 1` instead. Since `run_training.py` computes
`lr = base_lr * n_devices`, dropping from 4 devices to 1 would also silently
quarter the peak LR unless compensated — so these 3 configs set
`base_lr: 4.0e-5` (vs. `1.0e-5` for n0400-n12800) so the actual peak LR stays
exactly 4e-5 across all 9 variants, keeping sample count the only real
independent variable.

## Warmup schedule

`warmup_steps` is about one epoch's worth of steps, so the LR ramp does not
perturb the already-converged `exp01_zero_shot` checkpoint. It is computed
per variant from `n_train = N - max(1, int(0.05*N))` and
`steps_per_epoch = n_train // 8` (not divided by `devices`, so the value is
the same regardless of a variant's device count), floored at 10 steps to
avoid a degenerately short ramp at the smallest N. The `steps/epoch` and
`total_steps` columns are single-device counts (`total_steps =
steps_per_epoch * 20`). For the 4-GPU variants, `gap_aware_training.py`
divides steps per epoch by `devices` when it sizes the cosine schedule.

| Label | N | devices | base_lr | n_train | steps/epoch | total_steps (20 ep) | warmup_steps |
|---|---|---|---|---|---|---|---|
| n0050 | 50 | 1 | 4.0e-5 | 48 | 6 | 120 | 10 (floored) |
| n0100 | 100 | 1 | 4.0e-5 | 95 | 11 | 220 | 11 |
| n0200 | 200 | 1 | 4.0e-5 | 190 | 23 | 460 | 23 |
| n0400 | 400 | 4 | 1.0e-5 | 380 | 47 | 940 | 47 |
| n0800 | 800 | 4 | 1.0e-5 | 760 | 95 | 1900 | 95 |
| n1600 | 1600 | 4 | 1.0e-5 | 1520 | 190 | 3800 | 190 |
| n3200 | 3200 | 4 | 1.0e-5 | 3040 | 380 | 7600 | 380 |
| n6400 | 6400 | 4 | 1.0e-5 | 6080 | 760 | 15200 | 760 |
| n12800 | 12800 | 4 | 1.0e-5 | 12160 | 1520 | 30400 | 1520 |

## Directory layout / how to run

```
sample_ablation/
├── configs/n{0050,0100,0200,0400,0800,1600,3200,6400,12800}.yaml   — one config per variant
├── results/n{0050,0100,0200,0400,0800,1600,3200,6400,12800}/       — metrics.json + run_info.json once evaluated
├── results/RESULTS.md, loss_vs_samples.png                  — generated by the scripts below
└── scripts/
    ├── local/{train,evaluate}.sh                — CPU sanity check, all 9 variants, tiny model
    ├── slurm/train_all.sh, evaluate_all.sh       — n0400-n12800 fine-tuning (4-GPU) / all 9 evaluations (1-GPU), sequential steps in one job allocation each
    ├── slurm/train_small_all.sh                  — n0050/n0100/n0200 fine-tuning (1-GPU), sequential steps in one job allocation
    ├── slurm/train_n*.sh, evaluate_n*.sh         — real GPU runs, one script per variant
    ├── collect_results.py                        — aggregates results/n*/ + exp04 reference → RESULTS.md
    └── plot_results.py                           — eval MAE vs. N samples plot
```

**Local** (from the project root, `conda activate gap-aware`):
```bash
bash sentinel/experiments/exp02_finetuning/sample_ablation/scripts/local/train.sh
bash sentinel/experiments/exp02_finetuning/sample_ablation/scripts/local/evaluate.sh
```
CPU, tiny model, `--max_samples 10 --max_epochs 2 --batch_size 2` for every
variant — this only proves the 9 differently-configured variants
train/evaluate without error. A small local `gap_masks.lmdb` cannot reach the
real target sample counts, so meaningful numbers only come from the HPC runs
below. Local evaluation doesn't write
tracked results (matches every other experiment's local sanity-check
convention).

**HPC**.
`n0400-n12800` need a 4-GPU allocation (DDP); `n0050/n0100/n0200` need only 1
GPU (see "Method" above) — so they're two separate combined jobs. Evaluation
is always 1-GPU and covers all 9 in one job:
```bash
sbatch sentinel/experiments/exp02_finetuning/sample_ablation/scripts/slurm/train_all.sh        # n0400-n12800, 4 GPUs
sbatch sentinel/experiments/exp02_finetuning/sample_ablation/scripts/slurm/train_small_all.sh   # n0050/n0100/n0200, 1 GPU
# once both finish:
sbatch sentinel/experiments/exp02_finetuning/sample_ablation/scripts/slurm/evaluate_all.sh      # all 9, 1 GPU
```
The individual `train_n*.sh`/`evaluate_n*.sh` scripts run a single variant
in isolation (e.g. after a mid-sweep failure) without resubmitting a whole
`*_all.sh` job.

The `--time` budgets in the Slurm scripts are rough estimates. Adjust them to
the throughput of your hardware.
